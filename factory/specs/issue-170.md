## Outcome

Michael sets a weekly and a monthly budget in one small committed file (`factory/budget.yml`), dbt computes spend against both plus per-issue target and cap compliance, and `scripts/factory-site-data.py` exports the marts the site needs to `site-data/marts/<model>.json` deterministically, so the site generator needs neither dbt nor DuckDB.

## Context

Part of #169 (site data slice), built in parallel with #34. ## Design / approach

Make `factory/budget.yml` the single committed source of budget numbers and keep dbt `vars` as the mechanism dbt consumes. `scripts/factory-budget-vars.py` is a small pure-Python transform: load the YAML with the pinned PyYAML, validate with clear error messages (missing key, non-positive, and `weekly > monthly` each exit non-zero with a message on stderr), and emit a flat JSON object of dbt var names. It maps `monthly_usd` to the existing `deepinfra_monthly_budget_usd` var so nothing else must change, and adds `weekly_budget_usd` and `issue_target_usd`. The two new marts aggregate `fct_agent_runs` by ISO week and by calendar month (UTC) over a reporting window derived from a pinned `as_of_date` so builds are repeatable, computing `budget_usd`, percent used and an over-budget flag; `rpt_issue_target_compliance` groups per issue with under-target and under-cap flags plus a summary row. `scripts/factory-site-data.py` reads the built marts and writes one JSON file per model with a deterministic sort; it reads only a whitelisted subset of `fct_agent_runs` columns so no internal or sensitive columns leak into the site export. When dbt is skipped, the test feeds it the committed fixtures under `tests/site-data/sample-marts/` instead of a live dbt output directory.

## Alternatives considered

Optional for standard/normal but noted: keeping the budgets only as dbt `vars` (today's approach) was rejected because the issue and #56 explicitly want a committed `factory/budget.yml` as the owner-visible source of truth; deriving the budget file from the existing vars instead of adding it was rejected because Michael's dated values belong in one small file. Adding a separate mart per currency or provider was rejected to keep the marts small; the issue names exactly the fields wanted.

## Risks, rollback and revert trigger

Risk: a new mart or export introduces a divide-by-zero when a budget is zero or missing, or drops weeks with no runs. Mitigations: guard all divisions with nullif/zero checks and error on missing or zero budget; the weekly/monthly marts use a reporting window and fill missing weeks/months with 0 spend. Risk: `factory-budget-vars.py` could emit a var name that does not match a dbt var, breaking `dbt build --vars`; mitigated by mapping onto the existing `deepinfra_monthly_budget_usd` and adding the two new vars to `dbt_project.yml` in the same PR, and by the test script. Risk: the site-data export could be non-deterministic (dict ordering) or leak a non-whitelisted column; mitigated by deterministic sorting and a column whitelist, asserted by the byte-identical two-run check. Rollback is a normal code revert of the new files and the small `dbt_project.yml`, `schema.yml`, `README` and `.gitignore` edits. Revert trigger: if a dbt build with the new vars fails, or the weekly budget math is wrong (a row's percent used does not match spend/budget), or the site-data export is not byte-identical across two runs, revert.
